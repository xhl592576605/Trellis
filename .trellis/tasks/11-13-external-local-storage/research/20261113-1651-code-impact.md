## 已确认的范围边界

1. 不增加 Wiki 知识能力、不增加脚本转发 CLI、不改变任务阶段。
2. 外部是独立本地 Git 仓库；只做本地提交。真实代码仓库现有 remote/PR 能力不受此限制。
3. workspace 保留，但取消开发者子目录和身份初始化依赖。
4. finish-work 必须完成本次任务相关外部修改的提交，不夹带其他项目或任务的修改。
5. 项目内继续安装对应平台接入文件，并新增可浏览的 `.trellis` 链接。接入和脚本运行以配置为准，链接缺失不导致运行失效。

## B. 必须处理的运行时和平台缺口

- `packages/cli/src/commands/channel/context-loader.ts:45`：上下文 materialization 拒绝 cwd/受信目录之外的真实路径。

后果：Python task start 成功不意味着 Pi/OpenCode 能看到同一个任务；channel 也可能拒绝原有 JSONL/spec/agent 路径。

规划要求：只把经过绑定验证的当前项目外部目录加入合法根，保持现有 realpath/path-traversal 检查。禁止把整个 `~/.trellis-wiki`、用户主目录或任意绝对路径一并放开。

### B3 配置、链接、真实路径有三个状态，必须有一致性规则

当前 Python `get_repo_root` 和平台入口多以 `.trellis` 存在为依据。新模式必须以 `.treills.conf.json` 识别真实项目与数据位置，不能要求浏览链接存在。配置描述绑定，链接仅用于查看；配置无效必须清楚报错，错链/断链应告警并允许修复，不能影响有效配置决定的运行目标。

初始化/迁移需要处理：已有真实目录、已有正确链接、错误链接、断链、同名不同项目、路径包含空格/中文、用户目录缩写和 Windows 目录链接。

Windows 上评估 junction 作为本地目录链接的实现，避免要求所有用户开启 symlink 权限；创建失败必须保留可恢复状态，不得退化为复制一套独立数据。是否使用 junction 属于技术验证，不引入新的用户流程。

### B4 Hook 与 package 路径的语义不能随存储目录改变

- `packages/cli/src/templates/trellis/scripts/common/task_utils.py:382`：生命周期 hook 从 config 读取命令，但在真实 repo_root 执行，并传绝对 `TASK_JSON_PATH`。
- `packages/cli/src/templates/trellis/config.yaml:58`：monorepo package.path 描述源码目录。
- `packages/cli/src/templates/trellis/scripts/common/task_context.py:98`：JSONL 文件按 repo_root 拼接；项目内链接可保留原引用。
- `packages/cli/src/templates/shared-hooks/session-start.py:828`：当前 hook 从代码项目找到 `.trellis`，可经链接继续读取。
- `packages/cli/src/templates/snow/hooks/write-trellis-context.py:60`：Snow 也有独立的根查找和 task 引用解析，不能只验证共享 Python hook。

规划要求：代码操作和自定义 hook 的 cwd 保持真实 checkout；不把所有 repo_root 替换为 external root。模型启动前的 hook/plugin/extension 自行解析配置以完成 bootstrap；无 hook skill 先读同一配置，随后使用注入的外部真实路径。Python 脚本从真实 cwd 查找根配置、读取自己的外部数据。调用程序以 argv 执行外部脚本，保留已有 Python 选择/Windows 适配。

## D. Git 归属、提交范围和恢复

### D1 日志既查询代码证据，又查询自身 Git 历史

- `packages/cli/src/templates/trellis/scripts/add_session.py:379`：`git show <oid>^{commit}` 验证真实代码提交主题。
- `packages/cli/src/templates/trellis/scripts/add_session.py:605`：跨 refs 查询 journal 的最大 session 编号。
- `packages/cli/src/templates/trellis/scripts/add_session.py:653`：下一编号结合工作树及 Git 历史。
- `packages/cli/src/templates/trellis/scripts/add_session.py:709`：从 HEAD 读取日志内容，区分已提交与待恢复记录。
- `packages/cli/src/templates/trellis/scripts/add_session.py:1099`：自动提交也使用同一个 repo_root。

规划要求：代码分支/提交证据始终查询真实代码 Git；journal 内容/是否已提交/数据暂存提交查询外部 Git。不能只是对 `git add` 改 cwd。共享 workspace 编号和追加需要在项目级临界区完成，避免两会话拿到同一编号或覆盖 index。

### D2 “当前任务提交范围”已有基础，但现有收集器并不处处精确

- `packages/cli/src/templates/trellis/scripts/common/safe_commit.py:71`：任务级收集避免扫描其他 active task，但 journal 文件是共享的。
- `packages/cli/src/templates/trellis/scripts/common/safe_commit.py:144`：safe_archive_paths_to_add 在传 task_name 时仍加入整个 archive 子树，不能直接沿用为严格的单任务归档提交范围。
- `packages/cli/src/templates/trellis/scripts/common/task_store.py:1386`：归档提交使用显式 pathspec，已有防夹带 staged 文件的基础。
- `packages/cli/src/templates/trellis/scripts/add_session.py:1152`：journal 提交也使用显式 pathspec。

规划要求：保持用户已确认的“只提交本次任务”。精确包含归档源路径删除、对应目标任务目录及实际更新的父/子任务，不收集整个 archive。spec/config/research 等本次任务共享文件改动也要纳入完成检查，不只提交 task/journal。两个任务修改同一文件时，仅凭文件目录不可能判断每段改动的归属；实现需保护共享写入、明确本次提交范围，遇到已有混合修改不能默认整文件夹带。

### D3 归档失败恢复不同于日志失败恢复

- `packages/cli/src/templates/trellis/scripts/common/task_store.py:1350`：先清 session，再移动 task，最后尝试提交。
- `packages/cli/src/templates/trellis/scripts/common/task_store.py:1490`：部分 Git 失败返回与 source_was_tracked 相关，不能把现有退出语义直接当作“外部提交完成”。
- `packages/cli/src/templates/trellis/scripts/add_session.py:1164`：日志已有失败 checkpoint 与幂等恢复提示。
- `packages/cli/src/templates/common/commands/finish-work.md:53`：收尾先 archive 再 add_session；日志的 --commit 取代码工作提交，不是归档提交。

规划要求：外部提交失败时保留准确归档目标/任务身份，finish-work 不能由于 session 已清就遗漏未提交 task。重试应复用现有日志幂等机制，并验证实际提交完成。代码提交 hash 和外部数据提交 hash 分开报告。

### D4 现有 auto-commit 开关与“最终必须提交”需要明确契约

- `packages/cli/src/templates/trellis/config.yaml:21`：session_auto_commit=false 允许写文件但完全跳过 Git。
- `packages/cli/src/templates/trellis/scripts/common/config.py:107`：此开关共同控制 journal 与 archive 自动提交。

用户明确要求 finish-work 最终提交外部目录。设计必须交代旧开关迁移后的语义：可以保留单独脚本的中间步骤开关，但 finish-work 成功条件仍包含本任务外部变更已提交；不得静默跳过后报告已完成。不新增远程配置。

### D5 外部 Git 是共享事务资源

两个项目共用一个外部仓库的 index 和 HEAD。项目级日志写锁只能保护日志，不能保护另一个项目的 stage/commit；需要存储仓库级的短提交临界区，并保留其他 staged 修改。

初始化时验证指定 storage 确实为预期独立 Git 根目录，避免偶然沿用父仓库；缺少 Git 作者或提交 hook 失败时清楚报错并保留待恢复数据，不自动替用户设置身份、不自动绕过 hook。

## E. 卸载、可逆移除与链接

### E1 当前 uninstall 在链接场景下可能先删除外部目标内的受管文件

- `packages/cli/src/commands/uninstall.ts:1`：现有产品语义为移除所有 Trellis 文件及整个 `.trellis`。
- `packages/cli/src/utils/managed-removal.ts:239`：逐个 manifest key 构造待删除项。
- `packages/cli/src/utils/managed-removal.ts:318`：执行时先逐个 unlink，再 rm `.trellis`。

注意：风险不只是 `rm` 是否跟随 symlink。manifest 中的 `.trellis/scripts/...` 路径会穿过链接父目录，`unlink` 可能先删除外部脚本。必须先按代码接入/外部产品数据/目录链接区分归属。

### E2 Ablate 已经特殊处理 symlink，但 strict path 与新配置仍需适配

- `packages/cli/src/commands/ablate.ts:290`：applyAblationPlan 对 `.trellis` 为 symlink 时明确 unlink 链接，不递归删除目标。
- `packages/cli/src/utils/managed-removal.ts:133`：strict path 拒绝父目录链接逃出项目；manifest 含 `.trellis/*` 时在建立 plan 阶段就可能拒绝外部链接。
- `packages/cli/src/utils/ablation-store.ts:43`：fingerprint 有 symlink 类型，存链接目标而非自动证明外部数据快照。

规划要求：不要删除现有边界保护来让外部路径“通过”。新根配置也需要和链接一起移除/恢复，否则仅移除链接后，新配置仍可能让未来入口重新启用 Trellis。对于共享外部数据，不能在恢复当前 checkout 时覆盖另一 worktree 后续写入。

用户已确认：uninstall 断开当前 checkout 接入并保留外部数据；ablate/restore 只保存和恢复项目接入、根配置和浏览链接，不冻结或恢复共享外部数据。实现必须过滤指向外部数据的 manifest 条目，不能把旧逐文件删除逻辑直接用于外部模板。

## F. 迁移与边界

1. 先复制并校验、后切换配置与链接；已有真实 `.trellis` 绝不能直接覆盖为链接。
2. 重复运行应识别已完成、未完成和冲突状态，不复制出多个独立数据源。
3. 旧任务内 `.trellis/...` 引用需要通过明确的配置路径解析或定向迁移适配；新 runtime/注入不能从浏览链接寻址。外部规范/任务资料与真实项目 docs/源码的相对基准需要区分。避免重写历史文字或源代码字符串。
4. 多开发者旧日志都要保留，不能直接覆盖同名 journal/index；合并策略需要能保留原编号与历史作者，且不改变 task 的历史提交引用。
5. 代码 Git 历史留在原仓库；外部数据仓库从迁移快照开始。迁移引发的原目录跟踪删除要在真实项目中展示，代码提交仍走已有阶段。
6. 在代码目录执行和在外部数据目录执行含义不同。第一版保证现有从代码项目启动的流程；外部浏览不能导致脚本把 `.trellis-wiki` 误认成代码仓库。反向绑定作为默认入口，不能覆盖明确的当前 worktree。
7. 默认根、自定义根、大小写不敏感目录、空格/中文、Windows junction、断链/错链、多个 worktree 与不同 agent 安装均需进入验收矩阵。
8. 平台 sandbox 的外部读写能力需要实测：文件系统链接不等于宿主必然允许外部写入。使用平台已有配置能力，不能默认放开整个存储根。
9. `mem.ts:94` 按真实 cwd 筛选原始对话；channel bucket 和 worker cwd 也保持真实代码项目，不能随 external store 改变。
10. 用户授权的是规划。显式更新/迁移和保留外部数据的生命周期策略均已确认；产品代码和本仓库自身 `.trellis` 暂不迁移。

## G. 运行时定位方案比较与结论

| 项目 | 经项目内目录链接执行 | 配置解析并注入真实路径 |
| --- | --- | --- |
| 当前代码改动量 | 较少，可沿用部分 `.trellis` marker/相对入口 | 需要适配 Python 与各宿主的根发现和 bootstrap |
| 链接删除/损坏 | 任务可能无法发现或执行 | 配置有效时继续运行，可独立修复浏览入口 |
| 配置与链接不一致 | 容易形成两个运行目标 | 配置唯一决定绑定，链接不影响执行目标 |
| 跨平台目录链接限制 | 直接影响运行可用性 | 主要影响浏览功能，脚本本身不依赖链接权限 |
| 用户真实需求 | 浏览入口变成必需运行设施 | 符合用户明确要求 |

结论：采用配置解析并注入真实路径，软链接仅用于查看，不增加 CLI 转发层。为降低实现量，复用现有平台注册表、模板渲染与脚本本体；统一必要的路径契约及一致性测试，不重设计 task 工作流。

建议路径契约：真实代码根由当前 cwd/宿主上下文中的项目根配置定位；存储 Git 根与当前项目数据根由配置解析；scripts/workflow/tasks/spec/workspace/runtime 由数据根派生。代码 Git 命令仍使用真实 checkout。注入记录这些真实路径，不能注入一个依赖 `.trellis` 链接的替代入口。

## H. 现有更新/迁移机制的实际能力

- `packages/cli/src/types/migration.ts:13`：MigrationItem 仅支持 rename、rename-dir、delete、safe-file-delete；from/to 的契约是相对项目根路径。
- `packages/cli/src/commands/update.ts:2320`：已有 breaking migration 显式授权 gate；不带 --migrate 时可拒绝不完整升级。
- `packages/cli/src/commands/update.ts:2556`：--migrate 执行模板文件迁移；已有计划、冲突分类和用户修改保护可复用。
- `.trellis/spec/cli/backend/commands-update.md`：普通 full backup 会排除 tasks/spec/workspace 等用户数据，并且不跟随 symlink/junction；这个备份不能直接当作外移用户数据的完整备份。
- `.trellis/spec/cli/backend/migrations.md`：breaking 发布需 migrationGuide 与 aiInstructions，可通过现有更新提示/迁移任务引导用户显式执行。

因此，现有框架支持“显式更新与文件迁移”的操作模型，但当前没有现成的“外部根初始化 + 全量数据复制校验 + workspace 转换 + 根配置切换 + 浏览链接 + 两仓库归属”的事务。规划应复用现有 update/--migrate 的入口和发布指引，补充专门的存储迁移步骤/脚本；不能简单加一个 rename-dir manifest 就认为已经支持整目录外移，也不能使普通模板更新先覆盖旧运行时、再发现数据尚未迁移。
